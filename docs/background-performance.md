# 后台性能与功耗

优化目标是降低长期后台运行的 CPU 调度、无效定位和跨应用调用，同时保持快门受理、停止确认、过期状态和断线恢复的正确性。

## 已落实的调度调整

- 相机未通过授权、不能接收 GPS 或已断开时，释放 GNSS/卫星/NMEA 订阅，保留用户 GPS 开关记忆。相机就绪后自动恢复；手机显示“等待相机”。定位数据质量和过期判断不放宽。
- 控制、授权和迟到确认恢复期间维持 500ms 超时检查，命令和蓝牙回报仍立即处理。稳定连接使用 2 秒心跳，没有相机也没有已注册手表通道时使用 10 秒待机周期。没有新增唤醒锁、精确闹钟或常驻计算线程。
- 移除无变化的周期 UI 刷新；没有界面监听者时不投递 UI 回调。相机遥测和明确状态变化仍驱动界面更新。
- 已注册手表通道时，兜底节点查询从 5 秒放宽到 30 秒；通道未建立时保持 5 秒。小米服务连接事件和发送超时仍直接触发恢复。仅靠兜底查询才能发现的手表切换可能最多等待约30秒。

这些是可从调度路径确认的变化，不能直接换算成省电百分比。蓝牙/GNSS 硬件、相机遥测频率、系统后台策略和佩戴状态都会影响结果。

## Java、Rust/C++ 与 ARM 分包

当前 Android 业务代码为 Java/DEX，已检查的小米 SDK JAR 没有 `.so`，发布校验报告新增 `runtime` 和 `nativeAbis` 字段。现阶段采用一个通用 APK；拆成两个文件但携带相同 DEX 不会产生针对 ARMv7/ARMv8 的原生优化。

Android 的 [ART 会使用 JIT/AOT 编译](https://source.android.com/docs/core/runtime/jit-compiler)。这不证明所有 Java 路径足够快，也不证明换语言一定能减少后台耗电。Android 官方同时要求[减少 JNI 数据封送和跨语言调用](https://developer.android.com/ndk/guides/jni-tips)。

先在同样硬件条件下测量 CPU 时间、唤醒、分配/GC 和指令延迟，若协议解码、校验或序列化成为实际热点，再以同样协议向量和工作负载对照 Rust/C++，保留 Android 蓝牙/定位与小米 SDK 边界。如果届时引入原生库，再分别构建 `arm64-v8a` / `armeabi-v7a`，对各 ABI 独立验证；[ABI 的定义与适用范围](https://developer.android.com/ndk/guides/abis) 由 Android 官方文档说明。

## 真机验收场景

使用同一手机、系统、亮度、无线环境和相机固件，分别对照升级前后的相同时长：中转开启但无相机、相机待机/GPS关闭、相机待机/GPS开启、反复开始/停止录像、锁屏后断线与重连。

记录 Android 系统的应用耗电、CPU 时间/调度、GNSS 活跃时长、内存/GC，并核对 p50/p95 命令到相机确认的延迟。保留原始记录在仓库外，公开报告只放脱敏汇总。首次启动、充电和温度变化不应混入稳态结论。当前没有真机 A/B 能耗结果，因此没有承诺节电比例，也没有宣布语言重构已经通过性能验证。
